# Follent.net Business Site Engine

## Mission and operating priorities

This repository serves two purposes: **Follent.net is the commercial website and Growth-tier reference implementation**, and **the underlying engine is a reusable foundation for future small-business websites**. The intended live site demonstrates what the business sells; do not assume it is already launched or that its integrations are active. Check current configuration and documentation.

Preserve a static-first, fast, accessible, SEO-friendly engine with low dependencies, low operating costs and straightforward client cloning. Default client delivery is **GitHub → Cloudflare Pages → Cloudflare DNS → custom domain**. Follent's recorded deployment uses Workers Static Assets; follow README's separate Workers procedure and verify actual account settings rather than switching hosts to match the client default. A human developer should be able to understand and maintain it without learning a bespoke framework.

For significant work, identify whether it affects **ENGINE**, **FOLLENT**, or both:

- **ENGINE:** reusable layouts, components, tokens, configuration, SEO generation, navigation, form transport and documented patterns.
- **FOLLENT:** brand assets, service copy, package pricing, portfolio evidence and business details. Keep these customisations thin and in the content/configuration layers.

Prefer preserving the reusable engine over making a one-off Follent customisation slightly easier, unless explicitly instructed otherwise. Do not embed Follent names, locations, prices or provider assumptions throughout generic CSS, JavaScript or shared layouts. Reuse should simplify the next client build; avoid abstraction for its own sake.

## Ecommerce exclusion

This is a business website engine, **not an ecommerce engine**. Do not add carts, checkout, inventory, product catalogues, payment processing, shipping, fulfilment, customer ecommerce accounts, subscriptions, WooCommerce or Shopify SDK dependencies. Ecommerce projects are separate projects.

Château Follent ecommerce is intended to move to **https://chateaufollent.com.au/** using Shopify. This is business direction, not evidence that migration has completed. Do not retain old Follent ecommerce functionality or incorporate its platform into this engine.

## Static-first development and design

- Keep core content and navigation available as HTML without JavaScript. Browser scripts progressively enhance navigation, forms, conditional interfaces and optional analytics; do not render ordinary static content through JavaScript.
- Do not introduce React, Next.js, Vue, Angular, SSR, a database, CMS, persistent server, runtime Node dependency or package-heavy build system for routine work. Before a major dependency, explain the concrete need, why the existing static approach is insufficient, and the impact on Cloudflare deployment and client maintenance. Framework conversions require explicit approval.
- Build reusable patterns with the existing partials, CSS classes, configuration and documented modules. Do not invent a component framework or turn the engine into SaaS.
- Maintain coherent tokens for colours, typography, spacing and layout. Prefer reusable classes; avoid inline styles, arbitrary duplicated values and unapproved utility frameworks. Keep the generated brand variables driven by configuration.
- Follent's defaults are **Libre Baskerville** for prominent headings and **Montserrat** for body, navigation and buttons, self-hosted with `font-display: swap` and retained licences. Use a spacious, ivory-led 60–30–10 balance: Limestone Ivory `#F2F0EA`, Noir Follent `#0A0A0C`, Bordeaux Nocturne `#4A002E` for actions and restrained accents. Preserve “View packages” and “Start your project” unless instructed otherwise.
- Keep design professional, restrained and legible, with clear CTAs and strong mobile usability. Avoid excessive gradients, glowing/glass cards, pills, blobs, animation, endless card grids, fake dashboards and fabricated metrics. Label illustrative design studies honestly.

## Forms, automation, security and privacy

Preserve the separation **native HTML/CSS form → configurable endpoint/provider → optional automation → business systems**. Formspark is the default Growth infrastructure, not the product sold in customer-facing copy. Advanced providers and automation platforms must remain replaceable.

- Form visuals/fields live in `src/pages/content.mjs`; enhanced interaction in `assets/js/form.js`; provider transport in `assets/js/form-provider.js`. When replacing a native backend, update both HTML action/provider metadata and transport. `provider: "external"` with an HTTPS `externalURL` currently links to an advanced external form; it is not an implemented embed.
- Preserve accessible labels, native validation, required-field indications, consent text, spam protection, pending/duplicate-click protection, recoverable errors and clear success behaviour. Keep native `_redirect` and a **separate `_error`** destination, and `_append=false` to avoid leaking enquiry data into URLs. Never report success without provider acceptance; HTTP acceptance still requires independent notification/delivery verification.
- Unconfigured Formspark submissions remain disabled in HTML. Enabling them requires Growth, a real endpoint, reviewed privacy approval, retention wording and a privacy contact address. Preview builds disable forms and analytics. Do not bypass these safeguards or flip approval flags merely to make a check pass.
- Optional `form.formtrackEnabled` uses Formtrack on active Growth Formspark Contact forms only. Keep the single async script after form markup, its narrow CSP permission and provider-generated attribution inputs. Capture Contact-URL campaign parameters without introducing cross-page persistence or copying them into redirects/analytics. A blocked tracking script must not block enquiries. Read README before changing submitted field names or package IDs.
- Public form endpoints/IDs and Turnstile **site keys** may be configured publicly. API tokens, Turnstile **secret keys**, private credentials and privileged tokens must never enter committed configuration, HTML or browser JavaScript; keep them in provider dashboards or an appropriate secret store.
- Keep business-critical routing and automation outside front-end presentation. Use agreed webhooks, APIs or external workflows; Power Automate, Zapier, Make, Workers, Microsoft 365, Teams and CRMs are options, not mandatory core dependencies. A documented hook is not a delivered live workflow.
- Collect only necessary enquiry information. Explain its use and retain an accurate privacy notice. Do not add tracking or third-party scripts without a concrete need. Preserve optional GA opt-in, Do Not Track/Global Privacy Control handling, sanitised initial URLs and conversion events without enquiry contents.
- Preserve generated CSP hashes and narrowly scoped provider origins, MIME/referrer/permissions headers and frame restrictions. Do not weaken security globally to fix a small integration issue. Document any necessary exception and verify enabled services still work.

## Content, SEO, performance and accessibility

Use Australian English and confident, understated, transparent copy. AI assists internal production; strategy, design, useful copy and reliable delivery are the product. Human review remains required.

Never invent testimonials, clients, outcomes, awards, statistics, partnerships, accreditations, business history, locations or credentials. Use `TODO:` in source/docs or an unmistakable preview placeholder when facts are missing; never disguise placeholders as production proof. Follent.net, SydneyAWC/Sydney Amateur Winemakers Club and Château Follent may be cited only with verified scope and permissions, without fabricated commercial relationships or results.

Preserve unique titles/descriptions, canonicals, Open Graph/social metadata, semantic heading order, descriptive links, clean URLs, sitemap, robots and appropriate business/breadcrumb schema. Choose the business's correct Schema.org type; omit unknown facts and never manufacture ratings or a physical address. Do not add FAQ markup simply because an FAQ exists. Keep local identity/contact/service details consistent; avoid keyword stuffing and thin location-page generation.

Target **WCAG 2.2 AA good practice**: semantic HTML, keyboard navigation, visible focus, contrast, accessible labels/errors, skip link, meaningful links/alt text, sensible touch targets, reduced motion and responsive typography. Fix shared patterns so improvements benefit future clients.

Target approximately **95+ in Lighthouse Performance, Accessibility, Best Practices and SEO**, without gaming audits. Use static rendering, minimal scripts, efficient CSS, responsible fonts, appropriately sized WebP/AVIF/responsive images, explicit dimensions and below-fold lazy loading. Do not lazy-load the principal above-fold image. Record measurements honestly; lab scores are not production field guarantees.

## Deployment, migration and client cloning

For Pages projects preserve **production branch `main`, framework None, build `npm run build`, output `dist`, Node 22+**. Follow the selected hosting procedure in README; Workers is a separate deployment configuration. The local preview is a development tool, not production infrastructure. Keep generated `_headers` and `_redirects` compatible with static hosting and documented. Automatic non-main safeguards are Pages-specific (`CF_PAGES=1`); Workers/other staging builds require explicit `--preview`. Test safeguards when changing deployment logic.

Do not automatically change DNS, retire the old site or perform production cutover. Follow the authorised deployment scope, [migration-url-map.md](migration-url-map.md) and [LAUNCH_CHECKLIST.md](LAUNCH_CHECKLIST.md). Back up and inventory old URLs/assets, review mappings and verify destinations before removing anything. Emit only reviewed redirects. Never send unrelated wine/product URLs to the Follent homepage; use a verified equivalent Château Follent destination where appropriate. Preserve mail records, verify apex/www/SSL behaviour and retain rollback options.

A client clone should require configuration, branding/logo/images, approved business copy, package modules, SEO/schema, optional analytics/forms, a separate Pages project, a manually connected domain and QA—not restructuring the engine. Remove Follent-specific offers and proof when irrelevant. Keep README, CLIENT_SETUP, AI_CLIENT_BUILD_PROMPT, migration/launch documentation and QA evidence accurate as behaviour evolves. Human review covers facts, design, scope, privacy and migration.

## Verification and completion

For implementation/content changes, run the existing commands from the repository root:

```sh
npm test
npm run build
npm run check
```

Use `npm run preview` for local review at **http://127.0.0.1:4173**. For package-sensitive changes, check generated variants with `node scripts/check.mjs --dir .qa/essential` (and `.qa/professional`, `.qa/growth`); `npm test` creates those test builds.

For layout, accessibility, form or analytics changes, run relevant browser checks using the optional tooling documented in [QA_REPORT.md](QA_REPORT.md): `node scripts/browser-qa.mjs`, plus `--fixture garden` for reusable-template coverage. Routes derive from the manifest; 320/390/768/1440px layouts use intercepted/mocked external services. Ordinary QA preserves tracked artwork. Source social PNG export is explicit with `--social-only`; inspect that change and rebuild afterward, or use `--social-out .qa/social-export.png` for ignored review output. Optional dependencies belong under `.qa/tools`, not production dependencies. Use the documented HTML validator and `node scripts/lighthouse-qa.mjs` when relevant; Lighthouse requires local preview and supports a page subset.

Review navigation, keyboard/focus, forms/validation/error paths, links, HTML semantics, metadata/schema, sitemap/robots, redirects, image performance, analytics/privacy, headers, Australian spelling, pricing/GST and ecommerce exclusions. Scale browser/performance checks to affected behaviour; documentation-only changes need accurate instructions/paths, not unnecessary visual rebuilds. Do not claim checks that were not run.

Use `npm run check:launch` before an authorised production launch. Its failures can correctly identify incomplete business setup; report them without inventing details or marking reviews approved. Distinguish automated/mocked evidence from actual provider delivery, deployed redirects/headers, screen-reader/real-device checks and production performance. Recheck live integrations and the deployed domain at launch.

Completion means the requested work is verified and documented, with material limitations disclosed. Long-term success is a credible Follent sales site and an engine that becomes **simpler and faster to clone with each client**, while remaining understandable, portable, modular and free of ecommerce.
